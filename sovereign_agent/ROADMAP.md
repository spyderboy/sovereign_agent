# ROADMAP — sovereign_agent self-improvement

Fixes for weaknesses found operating this harness against old-car-radio
(2026-09-08, several-hour run). All three tasks touch only `supervisor.sh`
— `work.py` is locked for this pass (see `.sovereign_config.json`); the
one work.py fix from that session (cross-file dependency gating in
`run_task()`) was made by hand, not through this harness, since it's
core scheduling logic used by every project this tool runs.

## Phase 2 — No-progress circuit breaker

Found operating this harness against old-car-radio (2026-09-08/09, second
run): when a SINGLE task in a batch keeps failing the same way (observed:
"prompt too large" even after trimming) but work.py still exits 0 (it
skips/queues the task rather than escalating), supervisor.sh's own loop at
line 489-503 sees `more_work_remains` still true and loops immediately
forever — no existing safeguard catches this. The two existing circuit
breakers don't cover it: `FAST_EXITS` only fires when a whole work.py batch
returns in under 10s (this one took ~3 minutes per batch, doing real
retries), and `ESCALATION_COUNT`/`LAST_ESCALATION_TASK` only increments on
`EXIT -eq 2` (a genuine escalation) — a task that gets silently skipped
every batch never escalates, so neither counter ever moves. This was only
caught because a human was actively watching the log; unattended it would
have spun until manually killed.

- [ ] In supervisor.sh: add a no-progress circuit breaker to the main work loop — add a new function `current_remaining_count()` directly after the existing `more_work_remains()` function (currently lines 294-300, ending with its closing `}`), mirroring its exact `is_deep_mode` branching but returning the actual count instead of a boolean: `current_remaining_count() { local mode; mode=$(resolve_task_mode); if is_deep_mode; then "$PYTHON" "$SOVEREIGN/work.py" --project "$PROJECT" --queue-remaining-count "$mode" 2>/dev/null; else "$PYTHON" "$SOVEREIGN/work.py" --project "$PROJECT" --remaining-count "$mode" 2>/dev/null; fi; }` (this reuses the exact same two work.py flags `has_unchecked_tasks`/`has_queued_tasks` already call at lines 266 and 275 — do not add a new work.py flag). Add two new shared-state variables immediately after the existing `FAST_EXITS=0` (currently line 312): `LAST_REMAINING_COUNT=-1` and `NO_PROGRESS_COUNT=0`. Then, inside the `if more_work_remains; then` block (currently lines 491-496, the one that logs "Batch done — more tasks remain; looping immediately" and does `continue`), insert this check immediately after the `if more_work_remains; then` line and before the existing `log "${GREEN}Batch done...` line: call `CUR_REMAINING=$(current_remaining_count)`; if `[ "$CUR_REMAINING" = "$LAST_REMAINING_COUNT" ]` increment `NO_PROGRESS_COUNT=$((NO_PROGRESS_COUNT + 1))`, else reset `NO_PROGRESS_COUNT=0` and set `LAST_REMAINING_COUNT="$CUR_REMAINING"`; then if `[ "$NO_PROGRESS_COUNT" -ge 3 ]`, mirror the existing stuck-path style used by the escalation/fast-exit breakers just above it in this same file: `log "${RED}Remaining-task count stuck at $CUR_REMAINING for 3 batches in a row — refusing to spin${RESET}"`, `write_status "stuck:$START_AT"`, `echo -e "\n${RED}${BOLD}  ✗ STUCK — same task(s) failing identically across batches, not progressing.${RESET}"`, `echo -e "  Check logs/incomplete_tasks.md and the *-work.log for the repeated failure reason.\n"`, then `break` (do not `continue` — this must exit the loop like the other two breakers do). Do not change the existing `FAST_EXITS`/`ESCALATION_COUNT` logic elsewhere in this file — this is a third, independent breaker, not a replacement — task gate: bash -n supervisor.sh passes, and `grep -c 'current_remaining_count' supervisor.sh` returns at least 2 (the function definition plus its call site) and `grep -q 'NO_PROGRESS_COUNT' supervisor.sh` succeeds
